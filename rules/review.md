# Review

- **Parallel reviewers.**
  - When a task is finished, review the whole change before committing or merging it.
  - Run the reviewers in parallel, each as its own agent.
  - Simplicity: the smallest change that fully solves the task.
  - Design: stress-test the decisions behind the change.
  - Stack: one reviewer per technology, checked against its current docs.
  - Security: a focused review of the change.
  - Tests: every behavior change has a test that fails when it breaks, and the cases Case sets requires pass.
  - UI: a design critique and audit, skipped only when no UI changed.
  - Today these run as: `ponytail`, `grilling`, `ctx7` docs, `security-audit`, `impeccable`.
  - Check it: every reviewer has reported before the merge.
- **Review rounds.**
  - Repeat review rounds until a round finds no defect.
  - Rounds 1 and 2 review the whole branch.
  - From round 3, re-run only the reviews that had findings, on the commits since the last round.
  - From round 3, only defects count: wrong behavior, a crash, lost data, a store rejection, a broken rule.
  - Fix wording and style findings when they're cheap; they don't call for another round.
  - If round 4 still finds defects, stop and ask the owner: the change likely needs a decision.
  - Finish the rounds before merging, even when the work runs long.
  - Cut the rounds short only when the owner says so, or for a commit that only brings main into a reviewed branch, with no conflict resolved by hand: Tests and Design, on the merged result.
- **Close every finding.**
  - Fix every review finding, or record why it stands.
  - Fix clear defects in the same change.
  - A finding that needs a decision becomes an issue, and the work moves on.
  - That includes test runners' small findings: file them and fix them in the same round.
  - After fixing, re-run each reviewer whose area the fixes touched.
  - Check it: every finding is marked fixed, recorded or filed.
- **Review report.**
  - After every review round, show the owner one table, with a row for each reviewer the change calls for.
  - Columns: Reviewer, Result, Note.
  - Result: ❌ and the count of findings still open, such as "❌ 3"; ✅ when none is open; ➖ when the reviewer was skipped.
  - A finding closed under Close every finding is no longer open: the note says how, such as "2 fixed".
  - A report with no ✅ counts as no report: at least one reviewer ran and passed.
  - After a short round, the rows it didn't re-run keep their result, noted "unchanged since <commit>".
  - Note: one line on what the reviewer checked or found; for a skipped reviewer, why.
  - A missing row means that reviewer didn't run.
  - Keep one report per change, with each reviewer's latest result.
  - Save it for each commit being merged or pushed, so anyone can check later that the reviews ran.
  - Today it's saved as `slipway/reviews/<commit>.md` in the git folder all the repo's worktrees share.
  - Example: "Security ✅ no input or storage changed"; "Tests ❌ 1 the new button has no test".
  - Check it: each commit being merged or pushed has a saved report with at least one ✅ and no ❌.
- **Reviewers only read.**
  - Reviewers read the change; they never edit, commit or switch branches.
  - Reviewers don't start agents of their own.
  - Each finding gives the file, the line, what goes wrong and a fix.
  - Findings come ranked, most serious first.
  - Why: a reviewer that moves the branch can break another session working in the same checkout.
- **Lighter review for non-code.**
  - A change with no app code, like docs, scripts or tests, gets the simplicity and design reviews only.
  - Add the UI review when it changes what users see, such as the website.
- **Check the design doc first.**
  - Before filing a look-and-feel finding as a bug, check the design doc.
  - If the design allows what you saw, it isn't a bug.
  - Put it to the owner as a choice instead.
