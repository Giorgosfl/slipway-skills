# Test

- **Focused test per behavior change.**
  - Every change to behavior adds or updates an automated test for it.
  - The test checks that one behavior and nothing else.
  - It fails when that behavior breaks.
  - Prove it: break the behavior on purpose, watch the test fail, then restore it.
  - Removing a behavior removes its test.
  - Example: switching the sort to newest-first comes with a test that fails if the order flips back.
  - Check it: every behavior change in the diff has a matching test change.
- **Record the passing check.**
  - After each feature or fix, run its focused test.
  - Record the passing run in the commit message: the command and its result.
  - A commit without a recorded check counts as unverified.
  - Example: "Fix sort order" ends with "Checked: sort tests, 4 passed".
  - Check it: every feature or fix commit names the test it ran.
- **Plain-language test cases.**
  - Keep the app's test cases in the repo, so they grow with the app.
  - Each case has steps, an expected result and the screens to check.
  - Steps say what a user does; Expected says what a user sees.
  - For a server or API, the user is the client: steps are requests, Expected is the response.
  - Use only words a user knows: leave out element IDs, coordinates and tool commands.
  - Then any agent or person can run the cases, with any tool.
  - Each change adds, updates or removes the cases its behavior touches.
  - Example: "Import a CBZ file. Expected: the series appears in the Library with its cover."
  - Check it: someone who never saw the code can run every case.
- **Test on the real platform.**
  - Run the test cases where the app really runs, the way its users run it.
  - Mobile app: on its simulator or a device.
  - Desktop app: its installed build, driven the way a user would.
  - Browser extension: installed in the browser it targets.
  - CLI: in a terminal.
  - Server or API: a running instance, through its real interface.
  - Website: in a browser.
  - A preview or dev page of a device app helps development but never counts as test evidence.
  - Example: a React Native screen passes in the iOS Simulator, not in a web preview.
  - Check it: each test report names the platform and build it ran on.
- **Runner agents.**
  - Routine test-case runs use lower-tier, non-frontier models to keep costs down.
  - A runner reports each case's verdict with its evidence (see Verdicts).
  - Evidence shows what the runner saw and checked, such as a screenshot, value or state.
  - Escalate only cases with conflicting results or evidence to a higher-tier model.
  - Give that model the conflicting results and evidence to resolve the discrepancy.
  - A failing case sends the work back to fixing and review.
  - Example: a runner reports a clipped button, but its screenshot shows the whole button; escalate that case.
  - Check it: every case has a verdict and evidence.
  - Check it: every higher-tier run names the discrepancy it investigated.
- **Private data stays private.**
  - Test runs use invented sample data, never the owner's real data.
  - The sample data gets its own build or data folder, so a run can't touch the real data.
  - Use real data only when the owner chooses it and is present.
  - Capture only the app's own window, never the whole screen.
  - Delete each capture once it has served as evidence.
  - Keep real data and secrets out of commits, issues, logs and screenshots.
  - Example: a desktop app has a "Sample" edition with invented titles and its own data folder.
  - Check it: no capture or commit from a run shows anything but sample data.
- **Script what can be scripted.**
  - Script a test case wherever a script can prove its Expected.
  - A script can prove it when the result is readable: a label, a value or a state.
  - Keep AI runners for what only a look at the screen can judge, like layout and spacing.
  - Scripts are fast, cheap and give the same answer every run; AI runs cost time.
  - The plain-language case stays the source of truth, and the script follows it.
  - Example: "the series shows 12 chapters" is scripted; "the cover isn't cropped" goes to an AI runner.
  - Check it: each case an AI runner ran has an Expected no script could read.
- **Every bug gets a case.**
  - Every bug found gets a test case that would have caught it.
  - Write the case when the issue is filed, not after the fix.
  - It is a new case, or a tighter Expected in an existing one.
  - Name the case in the issue's "Done when".
  - The bug is fixed when that case passes.
  - Example: "cover missing after import" adds "Expected: the cover shows in the Library" to the import case.
  - Check it: every bug issue names a case, and that case fails before the fix.
- **Case sets.**
  - Before a merge, the required cases pass: the whole automated suite, plus a chosen set of plain-language cases.
  - The automated suite always runs in full, since it's cheap; scripted cases count as part of it.
  - Plain-language cases cost a real run, so a merge runs only a chosen set of them.
  - Mark the core cases, the app's daily paths, in the case files.
  - A merge runs every core case.
  - A merge also runs the cases the change can affect, directly or through shared code, and the ones it adds or alters.
  - A risky change runs every case: dependencies, build or config, permissions, or stored data.
  - So does a change to startup and the main screen, or a server's entry point and routing.
  - When unsure whether a case is affected, run it.
  - Before a release, run every case against the exact build being shipped.
  - Example: a change to the shared date formatter runs the core cases, the sort cases and every case that shows a date.
  - Check it: a merge's test report gives the suite result and the tested commit.
  - The merge's test report names the risky change kinds touched, or "none", and the shared code touched.
  - The merge's test report lists the cases run, each with why, and every core case is among them.
- **Verdicts.**
  - Each case gets one verdict: pass, fail or needs-human.
  - Each verdict has a one-line reason.
  - Needs-human means the runner can't tell; it blocks a release until the owner looks.
  - A case the runner can't run, such as one needing a real device, is reported as not run, never skipped silently.
  - Those cases run later as manual steps, with the owner.
  - Example: "needs-human: the page edge looks clipped on iPad; can't tell if that's the design."
  - Check it: the report covers every case Case sets chose, each with a verdict or "not run".
- **Test code.**
  - Pure logic gets behavior tests: inputs in, expected outputs out.
  - A test that searches the source checks only wiring whose breakage would be silent, never comments, copy or whitespace.
  - Fixtures stay small and give the same result every run.
  - No test depends on a live external service.
  - Each test runs on its own, independent of the others.
  - Name each test after the user-visible behavior it protects.
  - Example: "newest-first puts the latest-added series on top", not "sort test 2".
  - Check it: the suite passes offline, in any order.
