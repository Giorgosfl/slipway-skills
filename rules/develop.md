# Develop

- **Gotchas file.**
  - Keep a gotchas file in the repo, grouped by area.
  - Add a line when a trap costs real time.
  - Each line names the trap and its issue number.
  - Longer detail goes in a separate file for that area.
  - Remove a line once it is no longer true.
  - Read an area's section before working in that area.
- **Atomic.**
  - Every function, type, module and file has one responsibility.
  - Each has one reason to change.
  - A file that mixes concerns, such as routing, data and rendering, gets split.
  - A unit past about 150 lines is a signal to extract.
- **Clean code.**
  - Names say what a thing is or does.
  - Delete dead code.
  - Split a function instead of giving it a boolean flag that switches its behavior.
  - Write code plain enough to read without a comment explaining it.
- **DRY.**
  - The same logic, markup or styling written twice becomes one shared piece.
- **KISS.**
  - Make the smallest change that works.
  - Make it in the one place every caller goes through, not in each caller.
  - Use the platform's built-in feature before writing your own.
  - Use an installed dependency before adding a new one.
  - Use a plain function before a class or a factory.
- **SOLID.**
  - Add a feature by adding a new module, not a new mode to an existing one.
  - Depend on another module's small public interface, never on its internals.
  - The app's entry point only wires modules together.
  - Each module owns its own state.
- **Validate at boundaries.**
  - Data coming from outside is checked by a schema, once, where it enters.
  - Outside means forms, API and IPC calls, files, stored data, URLs and external services.
  - Use the schema instead of scattered type checks.
  - Read stored data leniently: a bad field falls back to its default on its own.
  - Read API and IPC input strictly: a bad field rejects the whole call.
- **Constants.**
  - User-facing text, limits, storage keys and routes each live in their own constants file.
  - A user-facing string or number written inline in the code is a bug.
  - Developer log messages stay inline.
- **Comments.**
  - Write a comment only for an outside constraint the code can't show.
  - Such as a platform gap, an OS rule, a browser quirk or a security invariant.
  - Design reasoning goes in the agent instruction files, not in code comments.
- **Direct code.**
  - Build for the uses the code has today, not ones it might have later.
  - Add an abstraction or a layer only when a current use needs it.
  - Hard-to-change choices, like data formats and public APIs, get design up front.
- **New dependency.**
  - Add one only for a problem the code has today.
  - It replaces code we would otherwise write ourselves.
  - It is actively maintained.
  - It works on our platform.
  - Its licence allows how we ship the app.
  - It has no known vulnerabilities, and its install scripts are checked.
  - Only a library that shapes the architecture, such as a data layer, needs a recorded decision.
- **Small chunks.**
  - Cut a large feature into chunks that can each be reviewed in one sitting.
  - Each chunk runs and is committed on its own.
  - Work through the chunks in order without waiting for a "go".
  - After each chunk, report what now works and what's next.
- **One commit per verified step.**
  - Commit each feature, fix or test checkpoint separately, once it is verified.
- **Check before done.**
  - Run the project's checks before calling any change done: format, lint, typecheck and the rest.
  - Fix what a check reports; silence a check only with a stated reason.
  - Keep git hooks on.
  - Skip a hook only for a deliberate reason, stated in the commit message.
- **Main use first.**
  - When building or extending a feature, plan which work runs on the side: fetching, downloads, sync, imports.
  - Side work never blocks what the app is for: the user keeps using it while that work runs.
  - Keep side work off the main thread, and cap how much CPU, memory and network it takes.
  - Split heavy side work into small pieces that yield to the user.
  - Example: a reading app keeps scrolling and switching books smoothly while new chapters download.
  - Check it by using the app's main feature while the side work runs.
- **Licence provenance.**
  - Before adding third-party content, verify its licence allows how we ship.
  - Content means anything we didn't make: fonts, images, icons, sounds, books, sample data, test fixtures and code copied from elsewhere.
  - Record each item's source link and licence in a sources file in the repo.
  - Credit it wherever its licence asks, such as an acknowledgements page.
  - Content without a verified licence stays out.
  - Example: test comics come from public-domain or Creative Commons sources, each listed with its link and licence.
  - Check it: every third-party file in the repo has an entry in the sources file.
- **Security stays.**
  - Keep every security measure in place, even when it blocks a test or shows a prompt.
  - That covers secure fields, credential storage and anything the app keeps private.
  - A change that weakens one needs the owner's OK first.
  - Raise it as a finding of its own, not a side note in a summary.
- **Commit messages.**
  - Write the subject as a plain imperative: "Add bookmark list".
  - Start with the verb, without prefixes like "feat:" or "fix:".
